# Phase 7 — Operations & Intelligence: delivery notes

Backend: 396/396 tests passing (328 carried over from Phases 1–6, unchanged and
still green, + 68 new). Migration autogenerated and round-trip verified
(upgrade → downgrade → upgrade) against a fresh SQLite database carrying the
full Phase 1–7 chain — this sandbox has no Postgres available to install
(package-repo access was blocked), so unlike Phase 5/6's notes this migration
has **not** been round-trip verified against a real local Postgres; run
`flask db upgrade` / `downgrade` once against the real deployment database
before relying on it in production. Frontend builds clean (`tsc -b && vite
build`); no automated frontend test suite exists anywhere in this codebase
(Phases 1–6 included — no test runner is even installed), so "frontend
critical-flow tests" is covered the same way every prior phase's own frontend
correctness was actually gated: a clean typecheck + production build, plus
manual verification of each new flow.

This phase adds five subsystems on top of the untouched Phase 1–6 foundation:
**support tickets**, **disputes**, **admin RBAC**, **audit**, and
**analytics/reports**. Each is a new top-level backend package (`app/support`,
`app/disputes`, `app/rbac`, `app/audit`, `app/analytics`, `app/reports`)
following the same models → service → routes/admin-routes shape as every
prior phase's modules, plus one new admin-user-management surface
(`app/users/admin_service.py` + routes on the existing `app/api/admin_routes.py`)
that Phases 1–6 never built.

## 1. Support tickets

- **Public/internal message visibility is enforced in the service layer, not
  just by a UI toggle.** `app/support/service.py:add_staff_message` requires
  the `support.manage` permission to set `visibility=INTERNAL`, and
  `list_messages_for_viewer`/`get_attachment_for_viewer_or_404` filter out
  internal messages (and any attachment posted under one) for every non-staff
  viewer at the query layer — SRS 5/14's "must separate internal notes from
  public messages" is a server-side filter, never a field the client can
  simply ignore.
- **`related_entity_type`/`related_entity_id` resolution is centralized and
  ownership-checked.** A ticket can reference an order/delivery/payment/
  refund/vendor/rider by its public ID; `app/support/service.py:
  _resolve_related_entity` verifies the requester actually has standing to
  reference it for the four order-lifecycle types (must be the customer, the
  order's vendor, or its assigned rider) before storing the internal ID — the
  same "resolve to internal ID with an ownership check" shape already used
  for reviews' and promotions' polymorphic targets in Phase 6. VENDOR/RIDER
  references only require the target to exist (a ticket is often *about* a
  vendor or rider the requester doesn't own).
- **Attachments are record-keeping only**, mirroring Phase 4's
  `RiderDocument`: a `reference` string, not a file. Real object storage is
  out of scope for this phase, same as it was for Phase 4's documents.
- **Ticket numbers are a random token, not the row ID**, matching
  `app/orders/service.py:_generate_order_number`'s existing pattern
  (`TCK-YYYYMMDD-XXXXXXXX`) rather than formatting the autoincrement ID —
  this was actually *required* here, not just stylistic: the ID isn't known
  until after insert, so a `NOT NULL` ticket_number column has to be
  generated up front the same way orders already do it.

## 2. Disputes

- **Money only ever moves through `app.payments.refund_service`.**
  `app/disputes/service.py:resolve_with_refund` is the single function in
  this entire phase that can result in a refund, and it does so by calling
  `refund_service.request_refund` (as the order's own customer — the
  function's contract requires customer ownership) followed by
  `refund_service.approve_refund` when approval is required. It never
  constructs a `LedgerEntry`/`FinancialTransaction` itself. The action is
  then recorded as `REFUND_ISSUED`/`PARTIAL_REFUND_ISSUED`, pointing at the
  resulting refund's public ID — SRS 6/14's "financial actions must call
  Phase 5 services; never directly edit balances" is structural, not just a
  convention: `app/disputes/` has no import of `LedgerEntry` at all.
- **`disputes.financial_action` is a distinct permission from
  `disputes.manage`.** Investigating a dispute, recording a note, and
  resolving one *without* money are all `disputes.manage`; only
  `disputes.financial_action` (granted to `FINANCE_ADMIN` and
  `SUPER_ADMIN`) can call `resolve-with-refund` — `OPERATIONS_ADMIN` and
  `SUPPORT_AGENT` can drive a dispute to the point of resolution but cannot
  authorize the refund themselves, which is the separation of duties SRS 8's
  role table implies but doesn't spell out as an explicit rule.
- **A dispute always anchors to an order** (every category in SRS 6 —
  missing/wrong/damaged item, late/failed delivery, payment issue — traces
  back to one), with delivery/payment/refund as optional narrower pointers
  and an optional link back to the support ticket it was opened from.

## 3. Admin RBAC

- **`AdminRole` is additive on top of the existing flat `UserRole.ADMIN`,
  not a replacement for it.** Every Phase 1–6 admin route still just checks
  `role == ADMIN`; the new `require_admin_permission` decorator in
  `app/auth/decorators.py` layers a fine-grained permission check *inside*
  that, used only by Phase 7's own routes plus the two new admin-user-
  management endpoints. Retrofitting the ~20 existing Phase 2–6 admin
  endpoints (finance, growth, logistics, catalog, orders) onto the new
  permission system was judged too large a change to make safely in this
  pass and is flagged below as a clear next step.
- **`User.admin_role_id IS NULL` means unrestricted, by design.** This is
  what makes the whole system backward-compatible: every admin account that
  existed before this phase (and any new one created without an explicit
  role) keeps exactly the access it already had. A SUPER_ADMIN scopes a
  staff account down by *assigning* one of the six roles from SRS 8 — access
  only gets narrower than "everything," never wider than what a plain ADMIN
  already had.
- **Roles/permissions are seeded lazily, not via the migration.** No prior
  phase's migration inserts seed data either (Phase 5's default commission
  rate and Phase 6's notification templates are both runtime get-or-create
  fallbacks) — `app/rbac/service.py:ensure_seeded` follows the same
  convention, running once per process the first time anything touches
  `list_roles`/`list_permissions`/`get_role_or_404`/`create_role`. The test
  suite seeds explicitly in the `app` fixture since its scoped-admin
  fixtures query `AdminRole` directly before any request necessarily runs.
- **`SUPER_ADMIN`'s permission set can't be narrowed or disabled** —
  `app/rbac/service.py:update_role` raises `ROLE_IMMUTABLE` for either —
  so it's not possible to accidentally (or maliciously, from a compromised
  lesser-privileged session) lock every admin out of the platform.

## 4. Audit

- **The Phase 1 `audit_events` table is extended in place, not duplicated.**
  SRS 11's ER diagram already models `USER 1:N AUDIT_EVENT`, and
  `event_type` is exactly SRS 12's `action` column by another name — every
  existing call site (`app/auth/service.py`, `app/logistics/
  admin_service.py`, `app/payments/admin_finance_service.py`) keeps working
  unchanged. Five new nullable columns (`entity_type`, `entity_id`,
  `before_data`, `after_data`, `event_metadata` — not `metadata`, which is
  reserved on `db.Model`) were added; `before_data`/`after_data`/
  `event_metadata` are JSON-serialized `Text`, the same "structured data in
  a Text column" approach this codebase already uses for
  `DeliveryZone.polygon_geojson`, kept portable across the SQLite test
  backend and Postgres rather than using a JSON column type.
- **`app/audit/service.py:record()` never raises** — exactly like
  `app/notifications/events.py:notify()`, a failure to write an audit row
  logs and swallows rather than rolling back the action it's describing.
  Wired into: ticket assignment and status changes, dispute status changes,
  dispute action recording, dispute refund resolution, admin role
  assignment, and admin user status changes.
- **Before/after payloads are only ever the specific safe fields the caller
  passes** (e.g. `{"status": "SUSPENDED"}`), never a whole model row — there
  is no generic redaction pass over arbitrary dicts, since that's an easy
  place to get an omission wrong. SRS 10's "never store credentials, tokens
  or payment secrets" is upheld by every call site only ever passing small,
  specific, already-safe fields, not by a filter.
- **No update or delete endpoint exists for audit events at all** — SRS 10's
  "protect audit records from ordinary alteration/deletion" is satisfied by
  omission: `app/api/admin_audit_routes.py` only exposes a paginated list.

## 5. Analytics & Reports

- **Every number is computed live from the authoritative Phase 1–6 tables**,
  via aggregate SQL queries in `app/analytics/service.py` — nothing is
  cached or duplicated into a separate analytics table (implementation
  prompt 5: "avoid conflicting duplicate business totals"). Finance metrics
  in particular walk the real double-entry ledger (`LedgerEntry` joined to
  `FinancialAccount` by account type) rather than re-deriving revenue from
  `Order.total`, so they can never drift from what the Phase 5 ledger
  actually balances to.
- **`finance.view` gates the finance dashboard specifically — `analytics.view`
  alone is not enough.** `OPERATIONS_ADMIN` has `analytics.view` (for the
  orders/delivery/customer dashboards) but not `finance.view`, so it cannot
  see revenue/commission/payout figures through the general analytics
  permission — a deliberate separation-of-duties tightening caught by the
  test suite (`test_finance_admin_can_access_finance_but_ops_cannot`) rather
  than assumed.
- **Report generation is synchronous.** A `ReportExport` still models a real
  `PENDING → PROCESSING → COMPLETED/FAILED` lifecycle, but this phase
  generates the CSV in the same request (the underlying query is the same
  bounded aggregate the dashboard already runs) rather than dispatching to a
  background worker — swapping one in later is a change to *how* the status
  transition happens, not a schema change. Files are written under the
  Flask instance folder and only ever served back through an authorized
  download endpoint, never as a static path.
- **Scope reductions, documented rather than silently dropped:** vendor
  metrics aggregate at the vendor level, not broken out per-branch (SRS 9's
  "branch performance"); rider metrics don't separately report average
  delivery time per rider (the timing breakdown lives in the platform-wide
  `delivery_metrics` instead). Both are straightforward additive queries on
  top of what's already built.

## Admin: users, vendors, riders, orders, deliveries

Vendor/branch, order, rider, and delivery admin management already existed
from Phases 2–4 (`app/api/admin_catalog_routes.py`, `admin_order_routes.py`,
`admin_logistics_routes.py`). The one real gap this phase closes is **plain
user-account management** — there was no way for an admin to view or suspend
a bare account regardless of role (a customer, in particular, had *no* admin
surface at all before this phase). `GET/PATCH /api/v1/admin/users/{id}` and
`GET /api/v1/admin/users` fill that gap, gated by the new `users.manage`
permission, with every status change audited.

## Frontend

- Customer/vendor/rider: a shared `SupportPage` (Tickets / Disputes tabs,
  each with its own create modal) and shared `SupportTicketDetailPage` /
  `DisputeDetailPage`, reused across all three portals exactly the way
  Phase 6's `NotificationsPage` already is — role-aware only in which
  dashboard base path it links back to.
- Admin: `AdminSupportPage` (agent queue with status/category/unassigned
  filters) + `AdminSupportTicketDetailPage` (assignment, internal notes,
  status/resolution); `AdminDisputesPage` + `AdminDisputeDetailPage`
  (evidence, action history, non-financial resolution, and a separate
  refund-resolution panel); `AdminAnalyticsPage` (eight tabs, a date-range
  filter, stat grids and simple proportional-bar breakdowns — no charting
  library was added, consistent with this codebase carrying none); the
  tabbed `AdminRolesPage` (create roles from the full permission list,
  assign a role to any staff account, and an audit-log tab); `AdminReportsPage`
  (request/download CSV exports, save reusable report definitions); and
  `AdminUsersPage`, which replaces the `FutureFeaturePage` "reserved for a
  later phase" placeholder that sat at `/admin/dashboard/customers`.
- `Badge`'s shared status→tone map gained the new ticket/dispute/report
  statuses (`OPEN`, `IN_PROGRESS`, `WAITING_FOR_CUSTOMER`, `RESOLVED`,
  `INVESTIGATING`, `ACTION_REQUIRED`, `COMPLETED`) rather than introducing a
  parallel badge component.
- The admin sidebar gained five items (Support, Disputes, Analytics,
  Reports, Staff & roles) and "Customers" was renamed to "Users" pointing at
  the real page; customer/vendor/rider sidebars each gained one "Support"
  item. `AdminDashboard`'s quick-link grid was updated to match.

## Things deliberately left for a future phase

- The ~20 existing Phase 2–6 admin endpoints still gate on plain
  `role == ADMIN`, not the new fine-grained permissions — only Phase 7's own
  admin routes (plus the two new user-management ones) use
  `require_admin_permission`. Extending it to the rest is additive, not a
  redesign, but was judged too large a surface to change safely in this pass.
- No background worker for report generation — every export is synchronous
  today (see Analytics & Reports above).
- No real object storage for support/dispute attachments — `reference` is a
  secure pointer, same limitation Phase 4's rider documents already have.
- Vendor branch-level and rider per-rider delivery-time analytics
  breakdowns (see Analytics & Reports above).
- No automated frontend test suite (none exists anywhere in this codebase);
  no new rate limits were added to ticket/dispute creation — this mirrors
  the existing codebase's own selective use of `@limiter.limit` (only on
  auth and one rider-location endpoint across all of Phases 1–6), but
  user-generated-content endpoints like these are a reasonable candidate for
  one in a future pass.
